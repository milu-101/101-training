## 通用四問

### 1. 我的任務拆解

練習 2 是三張客訴，手上只有症狀。我先做的其實是把每張客訴對到系統的哪一頁、哪個流程，心裡有個大概位置再開工。接著決定一次只查一個 bug，不要三個混著看。每個 bug 對我來說都是同一套小循環：先想辦法重現，順著 Controller 往下追到 service、repository 找到根因，改掉，再回頭確認沒弄壞別的。三個就照這個節奏一個一個走完。

練習 3 是新功能，從 Controller 到 Repository 要動六個地方。我沒有一句話丟給它叫它寫完，而是先要它出計畫：哪些檔要新增或改、每層各放什麼、邊界怎麼抓、要補哪幾個測試。我看過、確認分層沒歪才讓它動手。回頭看這步很划算，計畫還是文字的時候改，比 code 都寫完再返工輕鬆太多。

練習 4 是重構 CreateOrderAsync。我沒急著搬 code，先把方法裡的邏輯一條條列出來，分成「驗證」和「組裝訂單」兩類，確認哪幾段可以整包搬走、搬走後行為不變，才動手。先規劃好如何調整，比邊改邊看穩得多。

### 2. AI 幫上大忙的地方

它會先把根因講清楚再動手，不是急著改。Gold 金額那題它直接說「建單時先打一次折、CalculateTotal 又打一次，所以是 0.9 × 0.9 = 0.81」，我對照 code 一看就懂，比自己 trace 快很多。

它自己把「重現 → 定位 → 寫測試 → 修 → commit」整套跑完。我的體會是：講清楚規矩（一 bug 一 commit）比手把手下指令好用，剩下的讓它自己安排。另外它有主動點出一件我沒想到的事——舊測試只驗了「總數」「最後狀態」，剛好都避開了會出錯的地方，這句提醒蠻關鍵的。

練習 4 重構前，它把方法裡每段邏輯先列成清單、標出哪些是純驗證、可以整包抽出來，還特別提醒錯誤訊息和檢查順序要一字不差。有這份清單墊著，我改的時候心裡有底，不是邊改邊猜。

### 4. 我會帶回日常工作的一招

修 bug 前，先把客訴翻成一句具體的斷言，寫成測試跑一次，**確定它是「因為這個 bug」才失敗**（不是編譯錯、不是資料沒建好），然後才動手改，改完看它轉綠。

以前我習慣先改 code、事後再補測試，結果常常補的是「一定會過」的測試，等於沒測到。順序反過來之後踏實很多。具體步驟：

1. 症狀寫成斷言（例：取消訂單後庫存要從 47 回到 50）
2. 跑 `dotnet test --filter <測試名>`，確認失敗原因就是那個症狀
3. 只改根因那一處
4. 再跑，該測試綠、其他測試不能被弄壞

練習 4 的重構是同一招反過來用：不補新測試、也不動舊測試，改完全綠就代表行為沒變——測試就是重構的安全網，敢動手全靠它。
