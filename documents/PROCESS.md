## 通用四問

### 1. 我的任務拆解

練習 2 是三張客訴，手上只有症狀。我先做的其實是把每張客訴對到系統的哪一頁、哪個流程，心裡有個大概位置再開工。接著決定一次只查一個 bug，不要三個混著看。每個 bug 對我來說都是同一套小循環：先想辦法重現，順著 Controller 往下追到 service、repository 找到根因，改掉，再回頭確認沒弄壞別的。三個就照這個節奏一個一個走完。

練習 3 是新功能，從 Controller 到 Repository 要動六個地方。我沒有一句話丟給它叫它寫完，而是先要它出計畫：哪些檔要新增或改、每層各放什麼、邊界怎麼抓、要補哪幾個測試。我看過、確認分層沒歪才讓它動手。回頭看這步很划算，計畫還是文字的時候改，比 code 都寫完再返工輕鬆太多。

練習 4 是重構 CreateOrderAsync。我沒急著搬 code，先把方法裡的邏輯一條條列出來，分成「驗證」和「組裝訂單」兩類，確認哪幾段可以整包搬走、搬走後行為不變，才動手。先規劃好如何調整，比邊改邊看穩得多。

### 2. AI 幫上大忙的地方

它會先把根因講清楚再動手，不是急著改。Gold 金額那題它直接說「建單時先打一次折、CalculateTotal 又打一次，所以是 0.9 × 0.9 = 0.81」，我對照 code 一看就懂，比自己 trace 快很多。

它自己把「重現 → 定位 → 寫測試 → 修 → commit」整套跑完。我的體會是：講清楚規矩（一 bug 一 commit）比手把手下指令好用，剩下的讓它自己安排。另外它有主動點出一件我沒想到的事——舊測試只驗了「總數」「最後狀態」，剛好都避開了會出錯的地方，這句提醒蠻關鍵的。

練習 4 重構前，它把方法裡每段邏輯先列成清單、標出哪些是純驗證、可以整包抽出來，還特別提醒錯誤訊息和檢查順序要一字不差。有這份清單墊著，我改的時候心裡有底，不是邊改邊猜。

### 3. AI 誤導我的地方，與我如何發現

### 4. 我會帶回日常工作的一招

修 bug 前，先把客訴翻成一句具體的斷言，寫成測試跑一次，**確定它是「因為這個 bug」才失敗**（不是編譯錯、不是資料沒建好），然後才動手改，改完看它轉綠。

以前我習慣先改 code、事後再補測試，結果常常補的是「一定會過」的測試，等於沒測到。順序反過來之後踏實很多。具體步驟：

1. 症狀寫成斷言（例：取消訂單後庫存要從 47 回到 50）
2. 跑 `dotnet test --filter <測試名>`，確認失敗原因就是那個症狀
3. 只改根因那一處
4. 再跑，該測試綠、其他測試不能被弄壞

練習 4 的重構是同一招反過來用：不補新測試、也不動舊測試，改完全綠就代表行為沒變——測試就是重構的安全網，敢動手全靠它。

### 記下來的三件事

- **省下的不只是步數，是「每一步都可能錯」的風險**：Off 那條路上，找 sqlcmd、湊參數、修編碼這些跟業務無關的雜事吃掉大半力氣，而每次重試都是一次可能放棄或將錯就錯的機會。
- **最關鍵的一點——`IsActive` 是我主動去讀 repository 才發現的**。若當時偷懶直接 `WHERE StockQuantity < 5`，這次剛好沒有停售的低庫存商品，答案會看起來一模一樣：**錯誤不會浮現，只會潛伏**。哪天有人把某個低庫存商品下架，這個查詢就開始默默給錯答案。所以 MCP 真正交付的是「正確性的歸屬」——規則封在 server 裡一次，沒工具時它落在每一個呼叫者身上。這跟活動 1 bug 2「折扣只留一份真相」是同一堂課。
- **description 就是 agent 唯一的使用說明**：On 那邊我一眼選對工具、還知道結果已排序、已濾掉停售品，全靠那句 description。它不是註解。

## 活動 2 練習 5c — Resource 和 Prompt 到底換到了什麼

**日期**：2026-07-31　**分支**：`feat/orderhub-mcp`

### 折扣規則用 Resource 給 vs. 讓 agent 自己去讀 `OrderService.cs`

我先問自己：讓它自己讀，會發生什麼？它得先找到檔案，看懂那個 `switch`，再從 `Math.Round(subtotal * (1 - rate), 2)` 推出「折扣是打在小計上、四捨五入到分」。這串推論每問一次就要重跑一次，而且它有機會讀錯——`CreateOrderAsync` 裡「快照存原價」那段附近就很容易讓人誤會折扣是在建單時打的（活動 1 的 bug 2 就是這麼發生的）。

Resource 是把**結論**先講好：寫一次、進版控、全隊共用，agent 取用的成本接近零，也沒有推錯的空間。

不過我在做的時候發現一個陷阱：範本給的 resource 是把「Silver 95 折、Gold 9 折」硬寫在字串裡。如果照抄，就變成折扣規則有兩份真相——`OrderService` 改了、resource 不會跟著改，而且它還很有說服力地在那裡騙人。所以我改成注入 `IOrderService`，用 `Enum.GetValues<CustomerTier>()` + `GetDiscountRate(tier)` 動態組出來：

```
- Standard：不打折
- Silver：折扣 5%（即 9.5 折）
- Gold：折扣 10%（即 9 折）
```

這些數字是真的從程式碼算出來的。所以差別不是「Resource 比讀 code 好」這麼簡單——**Resource 給的是結論，但那個結論必須指回唯一的真相來源**，不然它只是一份寫得比較好看的過期文件。

### Prompt 範本放在 server vs. 每個人自己打一段話

自己打的問題不是「麻煩」，是**產出不一致**。採購同事問低庫存報告的措辭跟我不一樣，想要的欄位也不一樣，出來的東西就不能互相比較；老實說我自己前後打兩次都不會完全一樣。等到報表要多一欄「上次補貨日」，我得去通知每一個人各自改自己的那句話——然後總有人沒改。

放在 server 是一份、改一次、`git log` 看得到誰為什麼改。

### 兩題其實是同一題

判準就一句話：**規則改版的時候，要改幾個地方？**

答案是「一個」就對了，「每個人各自一份」就是設計沒做完。折扣規則、報表話術，兩者都是把知識從**個人腦袋**搬進**版控的 artifact**，對象不同而已——一個是程式碼裡的規則，一個是問法。

這件事在這次訓練裡出現第三次了：活動 1 bug 2「Gold 折兩次」、MCP 練習 1「金額別自己算、一律叫 `OrderService`」、現在是「resource 別自己抄」。換三種形式考同一個原則，它就不是某個 bug 的補救，而是這個專案的結構性約束——**規則只能有一份真相，其他地方一律引用**。

### 順帶想清楚的：三個原語怎麼分工

**Tool 是動作、Resource 是資料、Prompt 是範本。**

折扣規則沒有參數、不打 DB、也不是一個查詢動作，所以它該是 Resource。做成 `get_discount_rules()` 工具就是把**背景知識偽裝成動作**，agent 得多花一次呼叫才拿到它本來就該先知道的事。反過來 `low_stock` 要查 DB、結果隨時在變，做成 Resource 就會給出過期快照——這不是假設，練習 4 取消訂單 1 之後 SKU-1032 從 4 補到 5，就直接脫離了練習 3 那張「庫存低於 5」的表。
