## 通用四問

### 1. 我的任務拆解

（開工前你把任務拆成哪幾步？實際做的時候順序有變嗎？為什麼變？）

- 原本想：三個 bug 一起看完 → 一次改完 → 一起 commit。
- 實際做的順序改成「一個 bug 走完整條流程再換下一個」：**建分支 → 寫一個會失敗的回歸測試（紅）→ 確認紅燈原因就是客訴症狀 → 修根因 → `dotnet test` 全綠 → commit → 回 main 開下一個分支**。
- 為什麼變：三個 bug 分屬分頁、金額、庫存三個不同區塊，混在一起改，commit 會糊成一團、出事也難回溯。拆成「一 bug 一分支一 commit」後，每個修改都能單獨 review、單獨 revert。

### 2. AI 幫上大忙的地方

（哪件事 agent 做得又快又好？**貼上當時的提問原文**，說明為什麼這樣問有效。）

- 提問原文（我給的）：
  > 「根據練習 2 的幾個 bug 修復，分開 branch 和 commit，一個 bug commit 一次，然後自己寫入心得」
- 有效的原因：我沒有丟「幫我修 bug」，而是把**約束條件**講清楚（一 bug 一分支一 commit）。agent 因此自己套用了系統化除錯 + TDD 的流程，並且在動手前先把三個根因用一句話講清楚：
  - 分頁：`Skip(page * pageSize)`，但 page 是 1-based，第一頁就多跳一整頁（off-by-one）
  - Gold 金額：建單時 Gold 先把折扣打進 `UnitPriceSnapshot`，`CalculateTotal` 又打一次 → 折兩次（0.9 × 0.9 = 0.81）
  - 庫存：先把 `order.Status` 設成 Cancelled，才拿它判斷要不要回補 → 條件恆為 false
- 最有價值的一手：它主動指出「舊測試只驗了**總數 / 最終狀態**，沒驗會壞掉的那個行為」，直接點出測試的盲區。

### 3. AI 誤導我的地方，與我如何發現

（agent 說錯／改錯／過度自信的時刻。你靠什麼抓到——對照程式碼？頁面實測？跑測試？）

- **它把心得寫錯檔案。** agent 看到 `training-repo/PROCESS.md` 就直接往裡面寫練習 2 心得，沒先確認心得模板其實在 `documents/PROCESS.md`。這是「就近取檔、沒先確認」的過度自信。我靠的是**自己知道檔案結構**，直接指出正確路徑才更正。教訓：agent 對「檔案該放哪」的假設要驗。
- **一個我事先擋掉的誤導**：Gold 金額 bug 有兩個可下手的地方（改建單、或改 `CalculateTotal`）。改錯地方會讓 Silver 一起壞掉。這裡是靠**既有測試**定錨——`CalculateTotal_AppliesTierDiscountOnSubtotal` 已經寫死 Gold 1000 → 900、「快照存原價、折扣只打一次」，所以確定該動的是建單那段預打折，不是 `CalculateTotal`。
- 共通的抓法：**跑 `dotnet test`**。每個修法都先讓新測試紅、修完轉綠（最終全綠），不因為 agent 說明聽起來合理就相信。

### 4. 我會帶回日常工作的一招

（一個具體、可複製的做法，不要寫「要多驗證」這種口號——寫出**操作步驟**。）

- 「**先寫會失敗的回歸測試，再修 bug**」的操作步驟：
  1. 把客訴症狀翻成一個具體斷言（例：取消訂單後庫存要從 47 回到 50）。
  2. 寫成一個測試，先跑 `dotnet test --filter <測試名>`，**確認它失敗、而且失敗訊息就是那個症狀**（不是編譯錯、不是別的原因）。
  3. 才動手改程式，只改根因那一處。
  4. 再跑一次，該測試轉綠、其他測試維持全綠。
  5. 一個 bug 一個 commit，message 用「症狀 → 根因 → 修法」。
- 這招保證測試真的「咬」到行為，而不是恆真斷言；也保證修的是根因不是症狀。

## 自我驗證（做到哪個階段答哪題）

### 第一階段 — Agentic Coding

練習 1

1. 我能不看筆記說出三個專案（Web/Core/Infrastructure）各自的職責
2. 我核對過 agent 描述的建單流程，且**至少找出一處不精確或過度簡化的說法**
3. 我知道商業邏輯應該放在哪一層、新增頁面要動哪些地方

練習 2

1. 三個 bug 我都先在頁面上重現過，才開始找程式
2. 我給 agent 的資訊包含具體觀察（頁碼／金額數字／庫存數字），而不是只貼客訴原文
3. 每個修復都回到頁面驗證過症狀消失
4. 每個 bug 都補了一個回歸測試，`dotnet test` 全綠
5. 三個獨立 commit，message 說明症狀與根因
6. （思考題）為什麼原本的測試沒抓到這三個 bug？
   → 因為舊測試只斷言了**粗顆粒的結果**，剛好停在 bug 前一步：
   - 分頁只驗 `TotalCount` / `TotalPages`（總數對就過），沒驗「哪一筆真的出現在第一頁」——而 bug 正是**內容位移**，總數不受影響。
   - 取消只驗最終 `Status == Cancelled`，沒驗「庫存有沒有加回來」——`Status` 有被正確設定，錯的是它旁邊沒跑到的回補迴圈。
   - 金額的 `CalculateTotal` 測試是拿手動指定的 `UnitPriceSnapshot` 去算，繞過了「建單時寫入快照」那段——雙重折扣就發生在沒被測到的建單路徑。
   一句話：**測了「數字對不對」，沒測「該發生的副作用有沒有發生」。**

練習 3

1. `/Products/LowStock` 不帶參數 → 門檻 10 的結果；帶 `?threshold=3` → 結果隨之改變
2. `?threshold=0`、`?threshold=-1` → 頁面顯示驗證錯誤，不是 500
3. 售出數量欄位排除了 Cancelled 訂單（可用一筆已取消的訂單驗證）
4. 停售（已停售 badge）商品不出現在列表
5. 程式分層與命名跟既有的 Products 功能一致（請 agent 自我 review 一次，並自己確認）
6. 至少 3 個新測試，`dotnet test` 全綠

練習 4

1. 重構後 `dotnet test` 全綠
2. 我能說出這次重構「改善了什麼、沒有改變什麼」
3. 我有在 code review 的角度看過 diff（不是 agent 說好就好）
